# Project Phoenix - Customer API Contract

## 1. Purpose

This document defines the REST API contract for the Customer capability in
Project Phoenix.

The contract provides a stable interface between modern digital channels and
the Customer business capability.

The contract is independent of the underlying implementation. The same
business capability may be implemented through the existing COBOL/CICS path
or through a future modern Customer Service.

---

## 2. API Standards

| Attribute | Standard |
|---|---|
| Base Path | `/api/v1` |
| Payload Format | JSON |
| Transport | HTTPS |
| API Style | REST |
| API Version | v1 |
| Authentication | JWT |
| Authorization | Role-Based |
| Error Model | Standard Phoenix error response |

---

## 3. Customer Operations

| Operation | Method | Endpoint |
|---|---|---|
| Create Customer | POST | `/api/v1/customers` |
| Customer Inquiry | GET | `/api/v1/customers/{customerId}` |
| Update Customer | PUT | `/api/v1/customers/{customerId}` |

---

## 4. Create Customer

### Endpoint

`POST /api/v1/customers`

### Purpose

Create a new customer.

The service validates the customer information, assigns a customer ID,
checks for duplicate customer information, persists the customer, and
returns the operation result.

### Request

```json
{
  "customerType": "IN",
  "title": "MR",
  "firstName": "Rahul",
  "middleName": "",
  "lastName": "Sharma",
  "gender": "M",
  "dateOfBirth": "1992-08-15",
  "mobileNumber": "9876543210",
  "email": "rahul.sharma@example.com",
  "addressLine1": "100 Main Street",
  "addressLine2": "",
  "city": "Chennai",
  "state": "Tamil Nadu",
  "pincode": "600001",
  "country": "India",
  "homeBranchCode": "1001",
  "status": "A"
}

### Success Response

HTTP 201 Created

{
  "customerId": "0000000001",
  "status": "SUCCESS",
  "message": "Customer created successfully."
}

### Validation Error

HTTP 400 Bad Request

{
  "timestamp": "2026-09-01T20:00:00Z",
  "status": 400,
  "error": "Validation Error",
  "message": "Mandatory field missing",
  "path": "/api/v1/customers"
}

### Duplicate Customer

HTTP 409 Conflict

{
  "timestamp": "2026-09-01T20:00:00Z",
  "status": 409,
  "error": "Customer Already Exists",
  "message": "Customer already exists",
  "path": "/api/v1/customers"
}

6. Update Customer
Endpoint

PUT /api/v1/customers/{customerId}

Purpose

Update an existing customer.

The customer ID identifies the existing customer and is not generated by
the update operation.

The service validates the supplied customer information, verifies that the
customer exists, updates the customer record, persists the change, and
returns the operation result.

{

  "title": "MR",

7. Common Error Model

All API errors use the following structure:

{
  "timestamp": "2026-09-01T20:00:00Z",
  "status": 400,
  "error": "Validation Error",
  "message": "Mandatory field missing",
  "path": "/api/v1/customers"
}

### Field	Description
timestamp	Error occurrence timestamp
status	HTTP status code
error	API error category
message	Human-readable error message
path	API request path
8. HTTP Status Mapping
HTTP Status	Meaning
200	Successful inquiry or update
201	Customer successfully created
204	No Content
400	Validation error
401	Authentication failure
403	Authorization failure
404	Customer not found
409	Business conflict / duplicate
500	Internal server error

10. Implementation Independence

The API contract must not expose:

COBOL paragraph names
Indexed-file implementation details
Physical file names
Copybook implementation details

These remain internal implementation concerns.

The API contract represents business capabilities and resources.
